# Ops Console 合并设计

日期：2026-07-08

状态：已确认，等待规范复核

目标仓库：`database-workbench`（最终重命名为 `ops-console`）

## 问题

当前目录包含两个独立工具：

- `database-workbench`：React、TypeScript、Vite 前端与 Go API，提供 MySQL、PostgreSQL、MongoDB 和 Redis 工作台。
- `log-lens`：Next.js 前后端、PostgreSQL、Redis 与独立 Worker，提供日志上传、SSH 导入、索引、搜索、时间轴和实时 Tail。

两套工具拥有不同的入口、连接管理、视觉系统、应用运行时和部署方式。用户希望把它们合并成一个产品，通过统一登录和连接中心管理数据库与 SSH 连接，同时保留数据库和日志的独立专业页面，不牺牲任何现有功能。

`log-lens` 当前包含尚未提交的大量功能改动。这些工作树内容是迁移基线的一部分，不得通过重置、清理或仅从 `origin/main` 复制而丢失。

## 目标

1. 最终产品命名为 **Ops Console**，仓库目录最终命名为 `ops-console`。
2. 以 `database-workbench` 为基础仓库迁入 Log Lens 能力。
3. 对外只提供一个应用入口、一个应用镜像、一个 Go 应用进程和一个端口。
4. React 构建产物由 Go 服务嵌入并静态托管。
5. PostgreSQL 与 Redis 作为同一份 Docker Compose 中的依赖服务。
6. 提供账号登录、个人连接、团队连接与明确的角色权限。
7. 数据库与 SSH 凭据统一由服务端加密保存，浏览器和普通 API 不接触保存的明文凭据。
8. 使用统一的浅色工程工作台视觉系统；数据库和日志工作区仍通过独立路由和布局保持任务边界。
9. 以垂直切片方式迁移，每项功能经过新旧行为对照后才切换。

## 非目标

- 不把数据库操作和日志分析塞进同一个业务页面。
- 本轮不增加 OIDC、LDAP 或其他外部身份提供商；先实现内建账号体系。
- 本轮不设计插件市场或通用插件框架。
- 本轮不要求多副本横向扩容；结构上保留未来拆分后台 Worker 的可能性。
- 不借合并机会重做数据库查询、Schema、日志检索等已经工作的业务语义。
- 在新系统完整验收之前，不删除原 `log-lens` 项目、原始数据或上传文件。

## 已确认的关键决策

| 项目 | 决策 |
|---|---|
| 合并入口 | 一个域名和一个 React SPA |
| 页面边界 | 统一外壳；连接、数据库、日志、设置分路由 |
| 应用运行时 | 一个 Go 进程 |
| 依赖 | PostgreSQL、Redis 由同一份 Compose 管理 |
| 基础仓库 | `database-workbench` |
| 最终名称 | Ops Console / `ops-console` |
| 视觉方向 | 浅色工程工作台 |
| 凭据存储 | 统一服务端加密存储 |
| 访问控制 | 登录账号、个人连接、团队连接 |
| 迁移方式 | 垂直切片迁移与逐项质量闸门 |

## 方案选择

### 采用：垂直切片迁移

先建立统一外壳、身份、权限和连接中心，再依次迁移数据库接入与日志功能。每个日志能力从 UI、API、任务到数据存储完整迁移，并与旧系统进行结果和性能对照。

该方式在最终架构保持简洁的同时，把功能遗漏和回归限制在单个切片内。原项目在迁移期间仅作为基线与回滚来源，不作为最终运行时依赖。

### 未采用：后端优先整体重写

一次性把全部 Next.js API 和 Worker 改为 Go，架构收敛快，但较长时间无法进行端到端验证，容易积累行为差异。

### 未采用：前端优先代理旧服务

先做统一前端并代理旧 Next.js API，能快速看到合并界面，但过渡架构需要两个应用进程，容易让临时桥接变成长期依赖。

## 总体架构

```text
Browser
└── React SPA
    ├── /login
    ├── /connections
    ├── /database/*
    ├── /logs/*
    └── /settings/*
            │ HTTPS / JSON / SSE
            ▼
ops-console（单个 Go 进程）
├── 静态资源托管与 SPA fallback
├── identity     登录、会话、用户、团队、角色
├── registry     统一连接元数据、授权、加解密、审计
├── database     现有数据库连接、查询、表、Schema、Mongo、Redis 能力
├── logs         上传、解析、索引、搜索、上下文、时间轴
├── ssh          SSH 导入、远程同步、实时 Tail
├── jobs         进程内 Worker、Redis 任务领取、进度与重试
└── platform     配置、错误模型、健康检查、结构化日志
       │
       ├── PostgreSQL：账号、授权、连接、日志会话与索引数据
       ├── Redis：会话、任务队列、进度和短期运行状态
       ├── uploads volume：上传与远程拉取的原始日志
       └── 目标数据库与 SSH 主机
```

### 运行时约束

- Go 使用嵌入式静态文件提供编译后的 React SPA，未知非 API 路由回退到 `index.html`。
- 后台日志任务作为同一 Go 进程中的受控 Worker 池运行，不再部署独立 Node Worker。
- PostgreSQL 保存长期状态；Redis 只保存可重建或有 PostgreSQL 状态副本的短期状态。
- `/health/live` 仅表示进程存活；`/health/ready` 校验 PostgreSQL、Redis、迁移状态和关键配置。
- 最终镜像不包含 Node 运行时。Node 仅存在于构建阶段。

## 前端设计

### 技术结构

- 保留 React 19、TypeScript 和 Vite，增加客户端路由。
- 顶层 `AppShell` 只负责全局导航、账号菜单、页面容器和错误边界。
- `connections`、`database`、`logs`、`settings` 各自拥有独立 feature 边界。
- 数据库工作台的大型状态不提升到全局；日志分析状态也不与数据库状态耦合。
- 共享层只包含设计 token、基础控件、身份上下文、连接摘要和 API 基础设施。

建议路由：

| 路由 | 页面 |
|---|---|
| `/login` | 内建账号登录 |
| `/connections` | 统一连接中心 |
| `/database` | 数据库入口或最近工作区 |
| `/database/workspace/:connectionId` | 数据库工作台 |
| `/logs` | 日志会话列表 |
| `/logs/new` | 新建日志分析 |
| `/logs/sessions/:sessionId` | 日志分析详情 |
| `/logs/tail` | SSH 实时 Tail |
| `/settings/profile` | 个人资料 |
| `/settings/users` | 系统管理员的用户管理 |
| `/settings/teams` | 团队与成员管理 |

### 视觉系统

采用已确认的浅色工程工作台方向，以 Log Lens 的浅蓝灰 token 为基础统一两套 UI：

- 页面背景使用浅蓝灰，面板使用白色，主操作使用天蓝色。
- 顶栏、侧栏、表单、按钮、对话框、空状态和反馈信息使用同一套 token 与组件。
- 数据库编辑器、日志输出和上下文查看器可以保留深色终端表面，但边框、字号、工具栏和交互状态服从统一系统。
- 默认布局保持高密度工程工具属性，不把专业表格和编辑器卡片化或过度留白。
- 保留键盘操作、可见焦点、减少动效设置和现有虚拟滚动能力。

## 身份、团队与权限

### 身份体系

- 使用本地用户名和密码登录。
- 密码使用 Argon2id 与每用户独立盐保存，不保存可逆密码。
- 首位系统管理员通过部署时的一次性初始化配置或初始化命令创建；初始化完成后不可再次使用相同入口。
- 登录成功后签发高熵随机会话标识，存入 `HttpOnly`、`Secure`、`SameSite=Strict` Cookie。
- Redis 保存带 TTL 的会话状态；修改密码、禁用用户或角色变更时可立即撤销相关会话。
- 状态变更接口要求同源请求和 CSRF 防护。

### 角色

| 角色 | 权限 |
|---|---|
| 成员 | 管理自己的连接；使用所属团队允许使用的连接 |
| 团队管理员 | 管理团队成员；创建、编辑和停用团队连接 |
| 系统管理员 | 管理用户、团队和全局策略；不能通过普通 API 读取明文凭据 |

权限检查发生在读取连接详情、测试连接、建立运行时连接、启动日志任务和修改连接之前。前端隐藏按钮只改善体验，不能替代服务端授权。

## 统一连接模型

数据库与 SSH 使用同一顶层 `Connection` 实体，驱动特有字段保存在经过验证的配置结构中：

| 字段 | 含义 |
|---|---|
| `id`, `name` | 稳定标识和显示名 |
| `kind` | `database` 或 `ssh` |
| `driver` | `mysql`、`postgres`、`mongodb`、`redis` 或 `ssh` |
| `scope` | `personal` 或 `team` |
| `owner_user_id` | 个人连接所有者；团队连接为空 |
| `team_id` | 团队连接所属团队；个人连接为空 |
| `endpoint` | 主机、端口等非敏感寻址信息 |
| `config` | 数据库名、SSH 路径等经过 schema 校验的非敏感配置 |
| `encrypted_secret` | 加密后的用户名、密码、私钥或其他秘密字段 |
| `created_by`, `updated_by`, timestamps | 审计字段 |

### 凭据保护

- 保存的凭据使用 AES-256-GCM 加密，每条记录使用独立随机 nonce。
- 主密钥通过部署 secret 注入，不写入数据库、镜像、仓库或日志。
- API 列表和详情只返回脱敏摘要以及 `hasSecret`，不返回密文或明文。
- 连接执行路径在完成权限检查后才解密，明文只在 Go 进程内存中短暂存在。
- 错误、审计日志和结构化日志对连接串、密码、Token、私钥和查询参数中的秘密字段统一脱敏。
- 密钥轮换采用版本化密钥和受控重加密任务；旧密钥在全部记录迁移成功前保留。

### 使用流程

1. 用户登录并选择个人或团队连接。
2. Go 服务校验连接范围、用户身份和团队角色。
3. registry 模块解密凭据并构造一次性运行时连接参数。
4. database 或 ssh 模块执行操作。
5. 服务释放运行时资源，记录不含秘密的审计事件。

## 数据库模块

现有 Go 模块是迁移基础，保留以下行为：

- MySQL、PostgreSQL、MongoDB、Redis 驱动能力。
- 数据库、Schema、表、字段、索引和 Key 浏览。
- SQL 编辑、多标签、取消、分页和 CSV 导出。
- 表数据筛选、增删改、Schema 变更预览与确认。
- 显式事务、离开提醒和危险操作二次确认。
- MongoDB 文档、聚合、Schema 推断和索引操作。
- Redis Key 浏览、TTL、编辑和命令控制台。

主要变化是把浏览器提供的完整凭据替换为已授权的服务端连接 ID。运行时数据库连接仍有独立生命周期和超时，保存连接不等于长期保持数据库 socket。

## 日志模块

Log Lens 的 Next.js API 和 Node Worker 按垂直切片迁移到 Go，保持以下功能：

- 本地 `.log`、`.txt`、`.gz` 分片上传。
- SSH 保存连接、目录树浏览、远程导入和增量同步。
- 多服务、多节点日志解析、合并和时间标准化。
- PostgreSQL 批量写入与全文检索。
- 关键字、正则、服务、节点、等级和时间范围筛选。
- 上下文查看、Timeline Heat Ribbon 和游标分页。
- 索引进度、失败信息、取消和重试。
- SSH 实时 Tail 与断线反馈。
- 大结果集虚拟滚动。

### 任务模型

- 长任务先在 PostgreSQL 创建持久 job 记录，再把可重试任务引用写入 Redis。
- Go Worker 池通过原子领取或租约防止重复执行。
- job 处理器必须幂等；重试不得重复创建日志行或损坏会话统计。
- 进度写入 Redis 并周期性落入 PostgreSQL，前端通过 SSE 获取更新。
- 进程重启后，过期租约任务回到待处理状态；超过重试上限后进入明确失败状态。
- 用户取消会设置持久取消标志，解析、下载和写入批次在安全检查点停止。

## API 组织与错误处理

建议 API 命名空间：

- `/api/auth/*`
- `/api/users/*`
- `/api/teams/*`
- `/api/connections/*`
- `/api/database/*`
- `/api/logs/*`
- `/api/jobs/*`
- `/health/live`
- `/health/ready`

所有 API 错误使用统一结构：

```json
{
  "error": {
    "code": "connection_auth_failed",
    "message": "连接认证失败",
    "requestId": "req_7f44f65c",
    "details": {}
  }
}
```

- `code` 稳定供前端判断，`message` 面向用户，`requestId` 用于排查。
- `details` 只能包含安全、可展示的信息。
- 连接错误区分认证、授权、网络、超时、协议和目标策略拒绝。
- 后台任务区分待处理、运行、成功、失败、取消和部分完成。
- PostgreSQL 或 Redis 不可用时停止领取新任务，并通过 readiness 阻止错误切流。
- 前端各业务工作区设置错误边界，局部故障不应使整个 SPA 白屏。

## 数据迁移

### 迁移来源

1. Database Workbench 浏览器 IndexedDB 中的个人数据库连接。
2. Database Workbench registry SQLite 中的个人与团队连接元数据。
3. Log Lens PostgreSQL 中的 SSH 连接、日志会话、文件、索引状态和业务数据。
4. Log Lens 上传文件卷中的原始文件。

### 迁移规则

- 浏览器连接通过登录后的引导式导入迁移。用户解锁旧 vault 后，前端把连接逐条提交到新服务；服务成功确认前不删除本地记录。
- SQLite registry 使用一次性、可重复执行的迁移命令导入 PostgreSQL，并输出逐条结果报告。
- Log Lens 使用数据库迁移把现有表纳入 Ops Console schema；迁移前创建一致性备份。
- 上传文件尽量原位挂载或复制校验，数据库只在文件存在且校验通过后更新路径。
- 迁移使用稳定来源 ID 或映射表避免重复导入。
- 名称冲突不静默覆盖；保留两条记录并标注来源，交由用户合并。
- 任一批次失败时保留原数据和已生成的报告，允许修复后继续。

## 迁移阶段与质量闸门

### 阶段 0：冻结可复现基线

- 保存两个仓库的提交状态与工作树补丁。
- 以 `log-lens` 当前工作树而非仅 `origin/main` 作为迁移源。
- 建立完整功能清单、API 样例、真实日志样本、页面截图和性能基线。

闸门：两个旧项目可独立构建；核心流程和测试基线可重复运行。

### 阶段 1：统一地基

- 引入统一浅色设计 token、SPA 路由与 AppShell。
- 实现身份、团队、角色、会话和统一连接库。
- 建立 PostgreSQL、Redis、单 Go 应用容器的 Compose。

闸门：身份、权限、CSRF、会话撤销、连接加密与密钥配置测试通过。

### 阶段 2：数据库工作台接入

- 数据库前端改用统一连接 ID。
- 保持数据库模块业务实现，仅调整授权和连接解析边界。
- 提供旧 IndexedDB 连接导入流程。

闸门：现有 Go 和 React 测试全部通过；数据库功能清单逐项通过端到端验证。

### 阶段 3：日志功能垂直迁移

建议顺序：

1. 会话、文件和上传。
2. 解析、批量写入、索引和进度。
3. 搜索、筛选、上下文和时间轴。
4. SSH 连接、目录树、远程导入和增量同步。
5. 实时 Tail。

每个切片同时完成 React 页面、Go API、Go job handler、数据访问和测试。

闸门：相同日志样本在新旧系统产生等价的条数、时间范围、筛选结果和上下文；性能不超过约定回退阈值。

### 阶段 4：完整切换

- 执行全量回归、安全检查和大日志负载测试。
- 验证生产备份、恢复和回滚步骤。
- 确认最终镜像只有一个 Go 应用进程和一个对外端口。
- 切换完成后将产品与仓库重命名为 `ops-console`。

闸门：全部验收标准通过并由用户确认。旧项目和旧数据保留到观察期结束。

### 实施计划拆分

本设计是合并工程的总架构规范，不要求一次性实现。后续实施计划必须按以下可独立验收的子计划组织：

1. 基线保护、统一容器地基、身份与连接中心。
2. 数据库工作台改用统一连接模型。
3. 日志上传、解析、索引、搜索与分析页面迁移。
4. SSH 导入、远程同步与实时 Tail 迁移。
5. 数据迁移演练、完整回归、切换与仓库重命名。

每个子计划只能在前一子计划的质量闸门通过后开始生产切换。代码准备可以并行，数据迁移和流量切换必须按顺序执行。

## 测试策略

### 单元测试

- 密码哈希、会话、权限矩阵和连接范围。
- 加解密、脱敏、密钥版本与轮换。
- 日志解析、时间标准化、查询构造和上下文窗口。
- 数据库风险识别、Schema 操作和连接策略。
- job 状态机、幂等、租约、取消和重试。

### 契约测试

- React API client 与 Go handler 使用固定请求响应样例。
- 对旧 Log Lens API 建立行为样例，允许 URL 改变但不允许业务语义遗漏。
- 错误码、分页、进度和取消语义固定。

### 集成测试

- 使用真实 PostgreSQL 与 Redis 容器运行迁移、任务、全文检索和会话测试。
- 使用数据库容器验证 MySQL、PostgreSQL、MongoDB 和 Redis 驱动。
- 使用 SSH 测试服务验证认证、目录、下载、断线、重连和 Tail。

### 端到端测试

- 登录、创建个人连接、创建团队、共享连接、权限拒绝。
- 建立数据库连接并完成查询、事务、表编辑和危险操作确认。
- 上传日志并完成解析、索引、搜索、筛选、上下文和时间轴。
- 通过 SSH 导入日志并启动、停止实时 Tail。
- 刷新、会话过期、网络中断、任务失败和恢复。

### 性能测试

- 使用现有真实大日志样本记录上传吞吐、索引耗时、搜索 P95、首屏时间和内存峰值。
- 比较新旧系统的行数、索引大小、查询结果和资源使用。
- 数据库大结果集和日志大结果集继续使用虚拟滚动，不把全量数据装入浏览器内存。

## 可观测性与运维

- 所有请求生成 `requestId`，后台任务使用独立 `jobId`，两者在触发链上关联。
- 结构化日志包含模块、结果、耗时和安全的目标摘要，不包含秘密。
- 关键指标包括请求错误率、数据库连接数、任务队列长度、任务耗时、索引吞吐和 SSE 客户端数。
- Compose 为 PostgreSQL、Redis 和 Ops Console 设置健康检查与持久卷。
- 生产部署必须显式提供凭据主密钥和首位管理员初始化信息；不提供可用于生产的默认秘密。

## 风险与缓解

| 风险 | 缓解方式 |
|---|---|
| Go 重写日志路径产生语义差异 | 固定真实样本、旧 API 契约和逐切片结果对照 |
| 当前 Log Lens 未提交工作丢失 | 阶段 0 保存工作树状态；迁移读取当前工作树；禁止清理 |
| 单进程内 Worker 影响 API 延迟 | 有界 Worker 池、批量背压、资源限制和负载测试 |
| 服务端集中保存凭据扩大影响面 | 强认证与授权、AES-GCM、日志脱敏、密钥轮换和审计 |
| 浏览器旧连接无法自动读取 | 引导用户解锁旧 vault 后显式导入，保留旧数据 |
| PostgreSQL/Redis 故障导致任务不一致 | PostgreSQL 持久状态、幂等处理、Redis 租约和重启恢复 |
| 前端合并造成状态耦合 | feature 边界、独立路由、局部错误边界和最小共享状态 |

## 硬性停止条件

以下任一情况出现时不得切换生产流量：

- 旧功能清单存在未明确接受的缺失。
- 新旧日志解析或检索结果存在无法解释的差异。
- 数据库操作语义、危险操作保护或事务行为回退。
- 发现凭据泄露、越权使用或无法撤销的会话。
- 数据迁移无法备份、恢复或幂等重跑。
- 大日志处理、搜索或数据库工作台性能出现明显且未接受的回退。
- 最终应用镜像仍依赖 Node 运行时或需要第二个应用进程。

## 验收标准

1. 用户通过一个地址登录 Ops Console，并在统一连接中心管理数据库和 SSH 连接。
2. 个人连接仅所有者可管理；团队连接只对授权团队成员可见和可用。
3. 保存的数据库和 SSH 凭据均由服务端加密，列表、详情、错误和日志不泄露秘密。
4. Database Workbench 当前支持的所有数据库功能通过回归测试。
5. Log Lens 当前工作树支持的上传、SSH、解析、索引、搜索、时间轴、上下文和 Tail 功能通过回归测试。
6. 数据库与日志页面使用同一浅色设计系统、导航和基础控件，同时保持独立工作区。
7. Docker 构建产生一个应用镜像；运行时只有一个 Go 应用进程和一个对外端口。
8. PostgreSQL、Redis 与应用由一份 Compose 配置管理，健康检查和持久卷有效。
9. 旧连接、SSH 配置、日志会话和上传文件可迁移，失败可重试且不破坏源数据。
10. 单元、契约、集成、端到端、安全和性能闸门全部通过后才执行最终重命名与切换。
