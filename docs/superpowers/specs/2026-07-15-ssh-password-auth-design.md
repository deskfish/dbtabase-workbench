# SSH 密码认证与连接表单反馈设计

## 目标

让 SSH 连接同时支持密码认证和私钥认证，并确保保存失败时用户能在当前弹窗内看到明确、可操作的错误信息。

## 认证模型

- SSH 凭据允许包含登录密码、私钥以及私钥口令。
- 新建 SSH 连接时，登录密码和私钥至少填写一项。
- 私钥口令只在填写私钥时提交；单独填写私钥口令不构成有效凭据。
- 同时填写登录密码和私钥时，两者都写入现有服务端加密存储，连接阶段沿用服务端现有的认证尝试顺序。
- 数据库连接的用户名和密码行为保持不变。
- 编辑已有 SSH 连接时，所有凭据输入均为空表示保留服务端已保存的凭据。

## UI 设计

SSH 表单保留基础连接字段，并增加独立的“认证凭据”分组：

1. “用户名”作为 SSH 登录账号。
2. “登录密码”使用密码输入框，文案明确区别于私钥口令。
3. “私钥”使用多行输入框。
4. “私钥口令”位于私钥之后，并通过辅助文案说明仅用于解锁加密私钥。
5. 分组顶部显示“登录密码或私钥至少填写一项”。

字段校验错误贴近对应字段。接口返回的保存错误显示在弹窗内容区、操作按钮之前，使用 `role="alert"`，避免错误被遮挡在页面底层。提交期间保存按钮继续显示忙碌状态并防止重复提交。

## 数据流

前端表单转换层根据连接类型生成 `SaveInput`：

- SSH 密码认证：`secret = { username, password }`
- SSH 私钥认证：`secret = { username, privateKey, passphrase? }`
- SSH 混合认证：`secret = { username, password, privateKey, passphrase? }`

服务端 `registry.Secret` 已包含 `Password`、`PrivateKey` 和 `Passphrase` 字段，现有密钥环会整体加密序列化后的凭据，因此不需要数据库迁移。SSH 使用阶段已支持密码和私钥两种认证方法，保存层只需收到正确载荷。

## 错误处理

- 新建时没有密码和私钥：前端阻止提交，并在认证分组显示“请输入登录密码或私钥”。
- 只有私钥口令：视为缺少有效凭据，同时提示私钥口令需要配合私钥使用。
- 服务端返回权限、重复名称或存储错误：弹窗保持打开，在弹窗内显示服务端消息。
- 编辑已有且已有凭据的连接：允许凭据全部留空并保留原值。

## 测试与验收

- 表单转换单元测试覆盖密码、私钥、混合认证、无凭据和仅私钥口令。
- 页面测试覆盖 SSH 密码字段、提交载荷、弹窗内接口错误以及编辑时保留凭据。
- 前端完整测试和生产构建通过。
- 部署后检查应用健康状态，并通过生产页面验证 SSH 密码连接可保存且出现在连接列表中。

## 非目标

- 本次不新增连接前的 SSH 实时测试按钮。
- 本次不改变主机密钥校验策略。
- 本次不修改数据库连接认证流程。
